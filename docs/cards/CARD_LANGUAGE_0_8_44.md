# 卡牌描述规范：R 公司方案

描述规则版本：r-company-1。本规范统一机制复述 formal_text、词条 description、生成解释 explanation 和后续修改的文风；只更新表达，不改变玩家机制。下面的 R 公司例子是语言示范，不能把它们的效果或继承限制套到其他卡牌。

## 主句

- 写成“时机：条件，效果”。一个时机通常一行；简单机制一句，通常20～60字，复杂机制按时机分行，不为凑字数丢效果。
- 同一目标、时机和期限只写一次。用“+1/+1”“重甲+1”“行动费-1”“抽2张牌”。默认为控制者抽牌时省略“己方”；敌方抽牌、随机、选择、兵种及区域限制仍写清楚。
- 单位写“部署：”，指令直接写效果，不写“指令部署时”或多余的“使用本指令时”。附加能力中的“获得‘部署：抽1张牌’”必须保留触发词，不能删成“获得抽1张牌”。
- “本回合”“永久”等期限直接写入句子，如“本回合所有友方单位+2/+0”“行动费永久-1”，不堆叠“（本回合）”“（永久）”。“不含本指令”等引擎默认补充留给详情。
- 普通在场强化不反复写“本次在场期间”“直到离场”“再次入场重新计算”；默认规则不展开。永久、本回合、下回合、持续回合数、额外限制必须明确，不能把临时写成永久。
- 多个并列效果用逗号或分号；只有先后关系影响理解时用“随后”。不要每句都加“然后”“仅判定并结算一次”“无其他效果”。文字可合并同类，不能合并、删除或重排可执行能力组与操作，尤其不能把两次伤害改成一次。

## 词条与补充

- 卡面只显示词条名称、层数和卡牌自身效果，不在正文复述每个通用词条的解释。新词条的 description 仍须用一句话说明它自身的含义，不能只写名字。
- 继承来源、默认叠加与清除、同名去重、计数锁定等边界优先放详细说明。formal_text 没有单独的详情字段时，仅把本次需要玩家确认的特殊限制写成末尾短括号，不另写长篇“结算顺序”“引擎限制”。
- 例：“阵亡：将自身的复制洗入牌库。（仅继承【最后的孵化】的永久强化。）”用于确认指定继承来源；正式卡面的主句为“阵亡：将自身的复制洗入牌库。”，括号由详细视图展示。DSL 中 inherit_from 必须保留准确引用，不能因主句省略而扩大继承范围。
- 输出纯文本字符串，不在 JSON 文案中加入 Markdown 加粗、HTML 或自造的展示字段；词条加粗由游戏和网页统一处理。卡牌规则正文由程序渲染，explanation 不能代替可执行效果。

## 参考写法

- 兔子：“闪击\n阵亡：将自身的复制洗入牌库。”
- 驯鹿：“冲击\n行动后：+1/+1，行动费+2。\n阵亡：将自身的复制洗入牌库。”
- 犀牛：“守护\n每损失2点防御：重甲+1。\n阵亡：将自身的复制洗入牌库。”
- 最后的孵化：“弃置1张【集团军】单位手牌；己方场上、手牌和牌库中的同名单位永久+2/+2，行动费-1，获得‘部署：抽1张牌’；抽1张牌。”其中“【集团军】单位”保留名称包含筛选，不改成阵营筛选或完全同名筛选。
- 条件指令：“若敌方在场单位更多，抽2张牌。”
- 登场强化：“部署：重甲+2。”

## 多轮确认

最新修改优先，未撤销的要求继续保留。已经确认的数值、对象、期限不重问；常规缺省不机械提问。确有影响结果的歧义才放 questions，无法执行的要求放 missing_capabilities，不混进主句作长篇报错。修复 JSON 或继续对话时仍遵守本规范。

输出前检查：主句是否能直接读成卡牌文字；是否反复介绍相同目标或基础规则；是否完整保留永久/临时、随机/指定、触发、目标、条件和数值；是否误删被授予能力的触发词。禁止靠猜测补全玩家未确认的关键条件。
